# Signed releases and upgrade acceptance

Automatic updating remains deferred. The release path is a versioned, signed NSIS installer. Source gates and a successful signature check do not establish install or upgrade acceptance.

## Release prerequisites and commands

Use a trusted Windows build environment with the existing owner certificate already provisioned in `CurrentUser/My` or `LocalMachine/My`, a valid existing trust chain, an installed Windows SDK x64 SignTool, Bun, the normal build prerequisites, and an installed 7zip-compatible NSIS extractor (`7z.exe`, or an explicit `LUMEN_7ZIP` executable). This workflow does not create/import certificates, change trust, provision keys, or accept passwords/PFX content. If the owner supplies a PFX locator instead, provisioning the chosen certificate into the build account's store is a separate owner operation before these commands.

Set these nonsecret selectors in the build process: `LUMEN_SIGN_CERT_SHA1` (exact uppercase 40-hex thumbprint), `LUMEN_SIGN_CERT_SUBJECT` (exact certificate subject), `LUMEN_SIGN_CERT_STORE` (`CurrentUser` or `LocalMachine`), and `LUMEN_SIGN_TIMESTAMP_URL` (owner-approved HTTP(S) RFC3161 endpoint). `LUMEN_SIGNTOOL` may select an installed SDK executable. Repository variables with these same names configure tag CI; an absent certificate in the runner store blocks the release before expensive work. The current hosted runner is not provisioned with the owner's certificate by this change.

For signing CI, the owner must separately provide an existing trusted Windows x64 signing runner with the certificate/private-key access already available to its runner account, the required toolchain and existing Windows trust. Set repository variable `LUMEN_SIGNING_RUNNER` to that runner's unique label. Only pushed release tags select it; PR builds continue on `windows-2025`. A thumbprint alone cannot place a certificate in a fresh hosted runner. If the runner selector is absent, tag CI falls back to the hosted Windows runner and fails signing preflight rather than importing a key or publishing an unsigned artifact. No runner provisioning, PFX secret/import step, trust change or actual key transfer is implemented or performed here. Those are owner prerequisites; this workflow consumes the already provisioned store identity only.

Run `bun run release:preflight`, then `bun run release:build` in a fresh checkout/build directory. Set `RELEASE_TAG=v<version>` for tagged builds. Package, Tauri and Cargo versions must match; this first Windows release path accepts numeric `major.minor.patch` versions. Ordinary `bun run tauri build` and PR verification remain unsigned and usable without signing selectors.

The signed wrapper stages every normal pinned input before signing, including current static Rivet, stable Windows AI, Computer Use/PYD and SQLite vector copies. It preserves original bytes, source revision/dirty state and SHA256 inventory under `.build/release/originals-*` and `provenance.json`; it does not mutate upstream wheels/NuGet archives/vendor inputs. Verification rechecks Gateway's immutable upstream pin and proves changed PE bytes differ only in checksum/security-directory fields, alignment padding and an appended Authenticode table. Retained vendor bytes must remain identical. Retained signatures must pass current Windows trust/timestamp checks and exactly match `packaging/windows/retained-signers.json` (all primary/nested subjects, thumbprints and fixed resource prefixes). New or rotated vendor certificates require an explicit source policy review; unknown signed files are rejected rather than silently re-signed. Unsigned staged PE files, including PYD or extensionless PE, receive the selected owner signature using `/fd SHA256 /tr <endpoint> /td SHA256`.

After signing, `seal.json` records all final resource bytes and signature identities separately from upstream provenance. Before Rust compilation, `build.rs` runs fixed source verification of the seal, all staged bytes and real signatures, then embeds `lumen-release-v1:<seal-sha256>:<gateway-sha256>`. Gateway admission consumes that compiled digest; the complete binding passes through `black_box` so optimized linking retains the final package verifier's evidence. Runtime environment variables, adjacent manifests and arbitrary valid signatures cannot change Gateway admission. The release build marker is build-only `LUMEN_RELEASE_BUILD=1`, set by the wrapper; no Cargo feature is required, so unsigned `cargo test/clippy --all-features` remain ordinary verification.

Cargo reruns the build script on the build marker, certificate selector/subject/store, selected SDK tool and release tag, plus the release scripts/upstream pin/policy, product versions/config and complete binaries/resources/assets trees. Signed builds additionally watch `.build/release` including originals, seal and provenance; unsigned builds do not watch nonexistent signed-only files. Changing between unsigned/signed builds invalidates Cargo's build script output. A fresh signed seal is mandatory; an existing seal is refused rather than reusing stale signing output. Do not restage after sealing: native compilation, the before-bundle hook, and the final verifier all reject changed files. Each signed release uses a fresh checkout/build directory.

Tauri CLI 2.11.4's custom signer signs the patched main, generated uninstaller, five copied NSIS plugin inputs and completed installer. Before upload, `bun run release:verify` rechecks the staging seal and actual installer, lists and safely extracts its NSIS archive without running it, requires the actual main and generated uninstaller, verifies every extracted PE/PYD and every installed resource against the seal, and checks the main's current compiled binding. All five copied plugin inputs and each actually embedded plugin are verified; unused plugins need not be embedded. The extractor may emit `[NSIS].nsi` diagnostic text, which is recorded as extraction metadata and never treated as an installed executable. Missing extraction coverage fails closed.

`verified.json` binds the installer hash, owner identity, version, final binding and extracted inventory. Tag publication depends on successful Windows signing/verification; the publication job additionally verifies the downloaded installer's SHA256, tag/version and configured owner thumbprint before upload. No tag/release is created by local verification. PR installer artifacts remain unsigned evidence.

Optional sparse identity stays separate. Build it explicitly, ensure the actual certificate subject agrees with `AppxManifest.xml` and both fusion manifests, then use `packaging/windows/Sign-Identity.ps1` with the existing thumbprint/store and `-TimestampUrl`. Before signing and again during verification, the actual archive must match the validated source's namespace-aware manifest contract, including `Bridgehammer.Lumen`, both application IDs/executable targets, external-content and other declarations, plus every fixed asset's bytes. Renaming another same-owner/same-version package cannot satisfy this gate. Rebuild both executables if their fusion identity changes. Unsigned metadata fixture checks establish only this contract; actual trusted signed-MSIX acceptance remains pending owner material. An optional identity must never be represented as installed/registered just because it was signed. Framework availability, registration and Windows AI hardware/model acceptance remain separate.

## Owned clean-account acceptance runbook (pending execution)

Use an owner-provisioned disposable Windows account or VM with two correctly signed installers from distinct known revisions/versions, preinstalled WebView2/Edge, an owned profile and data, and recoverable VM/account snapshots. Do not run installers, uninstallers, app smoke/bootstrap or keyring checks in an ordinary account. `APPDATA`, `LUMEN_SMOKE_APP_DATA`, `/D` and `LUMEN_TEST_HOME` do not isolate the Windows account's fixed provider/tool-profile credential slots, Tauri Store/log KnownFolders, NSIS registrations, autostart or shortcuts. No account/VM creation or credential enumeration is part of this runbook.

Record Windows/account SID identity and ownership without recording credentials, source commits, all source gate outputs, installer hashes/signature reports, OS/WebView2/Edge versions, final inventories, and start/end times. Confirm the account is disposable and contains no ordinary Lumen data, KnownFolder `com.bridgehammer.lumen` directories in roaming/local AppData, Lumen processes, HKCU/HKLM product/uninstall registrations, autostart value, shortcuts or registered sparse identity. The existing smoke now refuses ordinary KnownFolder app data as well as its existing profile checks. Set `LUMEN_TEST_HOME` to an owned synthetic tool-profile root before any tool-profile action. Leave cloud grants off; use no live provider.

1. **Clean install:** Verify release A with `bun run release:verify` in its matching build/evidence checkout. Snapshot the clean disposable account/VM. Install A, record the actual registration/install directory and exact installed payload/signatures, launch only in that disposable account, and exercise ordinary local settings/search with synthetic roots. Existing `scripts/smoke-packaged.ps1 -ReleaseSealPath <A-seal.json>` may provide its unchanged clean-install native assertions in this account; it is not upgrade preservation proof and it uninstalls its own smoke installation. Keep its deadlines and all assertions unchanged.
2. **Preservation seed:** For a dedicated upgrade installation of A, select an owned synthetic search root with known files and indexed unique phrases; change a distinctive nondefault theme/shortcut/search setting and record the typed values and DB integrity/counts. Add only owned synthetic credential values through the app's existing supported credential interface in this disposable account. Check synthetic key equality locally and store only equality booleans, never values or credential-store dumps. Record any tool configuration fixture hashes. Close the app and confirm owned child processes exited; snapshot account/VM and copy the owned settings/SQLite data consistently (SQLite backup or closed process), verifying SHA256 and `PRAGMA integrity_check`.
3. **Upgrade:** Verify release B from its own checkout/evidence. Install B over A in the same disposable account and install location. Do not remove old data, check any delete-data option, reset credentials, or invoke fresh-default smoke as the upgrade assertion. Confirm B's installed version, signatures, final payload and Gateway binding. Launch B, assert the distinctive settings values, selected roots, original indexed phrase matches and synthetic credential equality booleans through supported app interfaces. Check DB integrity, record whether the existing index was retained or explicitly rebuilt, and inspect owned tool configuration fixture hashes. Do not expose secret values. Exercise local search and process start/Stop/exit with fixture-only providers.
4. **Interrupted upgrade and recovery:** Restore the owned A snapshot and confirm its signatures/seed assertions first. Start B's installer in this disposable environment; deliberately interrupt the installer at a recorded file-replacement phase using its exact owned PID, record exit/state and snapshot the failed state. Do not kill unrelated processes or mutate ordinary registrations. NSIS is not promised transactional: record whether A, B, or neither launches. Re-run the same verified B installer to recover. Require signed B payload, coherent version, integrity-checked preserved settings/index and synthetic credential equality afterward. A failed recovery remains a failed acceptance gate. If recovery fails, preserve the failed snapshot and restore only the owned clean snapshot for investigation.
5. **Uninstall and cleanup:** Close B and stop its owned children; run its actual signed uninstaller in the disposable account with delete-data disabled. Record installer/uninstaller exit codes and verify Lumen/sidecar/helper/Rivet/Cua/Job processes, install files, owned uninstall/product registrations, autostart and shortcuts are removed as expected. Check the documented user-data retention behavior without deleting the owned settings/index/credentials; an uninstall must not be mislabeled complete just because its window closed. Optional identity registration/unregistration, if tested, is a separately recorded owner operation in this disposable account. Restore/dispose of the owned environment only under its owner's existing procedure.

Acceptance is pending until all five stages have raw evidence and a reviewable result. Missing signer locator/private-key access in the selected store, a trust/timestamp failure, missing prior signed version, missing clean environment, missing final extracted artifact, preservation failure or leftover process blocks the respective gate. No live-provider, physical-device, Docker or production readiness claim follows from this source work.
